# ADR-005: События в реальном времени и клиент

## Контекст

Оператор должен видеть ход измерения без опроса: прогресс, графики, журнал и смену статусов
(FR-19…21, NFR-03: задержка не больше 1 с). Воркеры синхронные и живут в других процессах, чем
API, а клиентов может быть несколько.

## Решение

**События.** Воркер публикует JSON в Redis pub/sub: `events:job:{id}` (всё про задание) и
`events:global` (смена статусов заданий и приборов, без данных). API держит WebSocket-соединения
и пересылает сообщения подписчикам. Типы сообщений: `snapshot`, `status`, `progress`, `segment`
(`from_idx`, `freq_hz`, `s11_db`, `s21_db`), `log`, `error`, `instrument`.

- Публикация не должна ломать измерение: ошибки Redis при публикации логируются и
  проглатываются.
- Сообщения абсолютные (`points_done`, `from_idx`), а не приращения. Потерянное или повторённое
  сообщение не искажает картину.
- Pub/sub не хранит сообщения, поэтому история лежит в БД. Смены статуса, повторы и ошибки пишутся
  в таблицу `job_events` (`GET /jobs/{id}/events`), а сырые точки читаются из
  `GET /jobs/{id}/points`.

**Подключение (FR-21).** `/ws/jobs/{id}?token=...` и `/ws/events?token=...`. Сервер сначала
подписывается на канал Redis, потом читает состояние из БД и отправляет `snapshot`, потом
пересылает события. Так между снимком и потоком нет щели. Неверный токен закрывается кодом 4401,
неизвестное задание — 4404. Токен идёт в параметре запроса, потому что браузерный и Qt WebSocket
не умеют задавать заголовки. Это допустимо для внутреннего стенда, но токен попадает в логи
прокси, на публичной установке нужен короткоживущий билет для WebSocket.

**Клиент (PyQt6).**
- Все вызовы API идут через `httpx` в `QThreadPool`, результат возвращается в GUI-поток queued
  сигналом. GUI-поток сеть не трогает.
- WebSocket — `QWebSocket` в GUI-потоке (не блокирует). При обрыве соединение восстанавливается
  с паузой 1, 2, 4, 8, 10 … с. После восстановления карточка задания дозагружает точки и
  состояние, потому что события за время обрыва потеряны. Буфер хранит точки по индексу, поэтому
  дозагрузка и события не дублируются.
- При 401 клиент показывает окно входа, после входа переподключает потоки и перезагружает карточки.
  Refresh-токена пока нет (он появится вместе с ролями): повторный вход вручную.

## Последствия

- Доставка «не более одного раза»: клиент, не успевший подключиться, получает недостающее из БД.
- Каждое соединение держит подписку Redis и два asyncio-задания; для 5 приборов и нескольких
  операторов это несущественно.
- Данные сегмента идут в событии целиком (до 1000 точек × 3 числа): при большом `segment_size` это
  сотни КБ на событие. Для интерфейса оператора это приемлемо.
- Задержка зависит от опроса pub/sub раз в 250 мс в API (на реальном Redis ответ приходит сразу).
